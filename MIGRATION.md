# Migration: Chat Bubbles → Native Agent UI

## Overview

Transform the app from a chat-bubble-based LLM interface into a native-feeling agent interface with dynamic UI components generated by the LLM and MCP tools.

---

## 1. Architecture Comparison

### Current Architecture

```
LLM / MCP Tools
    ↓ raw JSON
Go Server → SSE events (text/thinking/tool_call/tool_result/metadata/done)
    ↓ line-buffered SSE
Flutter ApiService → SSEEvent stream
    ↓ switch(event.type)
_ChatScreenState._sendMessage → 7 hardcoded handlers
    ↓ setState
List<Message> → ChatBubble (role-based switch) → 7 bubble widgets
```

**Problems:**
- All content forced into chat bubbles (300px max-width)
- No markdown rendering — raw `SelectableText`
- MCP image/audio content silently discarded
- Tool result rendering hardcoded to 5 Sonos tool names
- No dynamic UI generation
- Grocery mode is a separate split-pane with duplicated chat logic
- No interactive elements (buttons, forms)

### Target Architecture

```
LLM / MCP Tools
    ↓ raw JSON + structured UI data
Go Server → SSE events (text + ui_blocks + ui_update + action)
    ↓ blocks pipeline
Flutter ApiService → SSEEvent stream (with blocks)
    ↓ parse & dispatch
ConversationProvider → List<Message with ContentBlocks>
    ↓ rebuild
ConversationStream → List<MessageGroup> → List<ContentBlock>
    ↓ WidgetRegistry (type → builder)
Native Flutter Components (Card, Table, Chart, Button, Form, ...)
```

## 3. Data Flow

### SSE Event to UI Component Pipeline

```
Go Server
  │
  ├── LLM response has ```component ...``` block?
  │     → Extract block, send as ui_blocks SSE event
  │     → Remaining text sent as text event
  │
  ├── MCP tool returns ContentItem with type:"component"?
  │     → Parse structured data, send as ui_blocks in tool_result
  │
  ├── MCP tool returns ContentItem with type:"image"?
  │     → Send as image block in tool_result
  │
  └── Regular text response?
        → Send as text event (rendered as markdown)

Flutter
  │
  SSEEvent stream → ConversationProvider.parseEvent(event)
  │
  ├── text event → Message.assistant(text) → parsed into ContentBlock(markdown, text)
  ├── ui_blocks event → ContentBlocks parsed from JSON
  ├── tool_result with blocks → ContentBlocks appended to tool result Message
  ├── ui_update → find ContentBlock by id, update its data
  ├── ui_action response → update component state
  │
  ConversationProvider.messages → ConversationStream
    → MessageGroup (by date)
      → ComponentSequence (role-indented container)
        → WidgetRegistry.build(ContentBlock)
```

### Action Callback Flow (Interactive Components)

```
User taps button
  → WidgetRegistry.build(button) → onAction("tool_name", args)
  → ConversationProvider.handleAction("tool_name", args)
  → ApiService.sendAction("tool_name", args)
  → POST /api/v1/action → SSE stream
  → Tool executed on server
  → tool_result + ui_blocks streamed back
  → Component updated/Message added
```

## 8. Key Design Decisions

### 8.1 ContentBlock Serialization
`ContentBlock` uses `Map<String, dynamic>` for data (not a sealed class hierarchy) to:
- Allow easy JSON serialization/deserialization
- Support forward compatibility (unknown types still store data)
- Keep the Go-to-Flutter data path simple (just JSON)

Type safety is provided at the WidgetRegistry level: each builder interprets `data` fields.

### 8.2 Backward Compatibility
Existing SSE events continue to work:
- `text` events → rendered as ContentBlock(type: markdown, data: {text: content})
- `tool_result` events → rendered as card or text block with tool name header
- `thinking` events → rendered as collapsible text block
- New `ui_blocks` events → rendered as registered component widgets

The existing `Message.content` field is kept but deprecated. New code uses `Message.blocks`.

### 8.3 MCP Content Types
The MCP `ContentItem` type is enhanced:
```go
type ContentItem struct {
    Type     string      `json:"type"`     // "text", "image", "audio", "component"
    Text     string      `json:"text,omitempty"`
    Data     interface{} `json:"data,omitempty"`     // For "component" — structured UI data
    MIMEType string      `json:"mimeType,omitempty"` // For "image" — "image/png", etc.
    Source   string      `json:"source,omitempty"`   // For "image" — "base64" or URL
}
```

The server passes `component` type items through as `ui_blocks` SSE events.
The server passes `image` type items through as `image` ContentBlocks.

### 8.4 LLM UI Generation
The system prompt is augmented with:

```
You can return structured UI components by wrapping JSON in 
```component
{...} 
```
 code fences. This renders as native UI. Use for: weather cards, stock metrics, data tables, comparison grids, etc. For plain text, respond normally.
```

The server's `handleChat` parses the LLM response text for ````component```` blocks, extracts them, sends as `ui_blocks` events, and sends the remaining text as usual.

### 8.5 Interactive Component Actions
When a user taps an interactive component (button, form submit):
1. Flutter fires `onAction(action, args)`
2. `ConversationProvider.handleAction` sends `POST /api/v1/action`
3. Server executes the tool, returns SSE stream
4. Results are either:
   - `ui_update` — update the component's content by ID (for toggles, sliders)
   - New `ui_blocks` + `text` — add new content to the conversation (for forms, buttons)

### 8.6 State Management
`Provider` + `ChangeNotifier` stays (already in use).
New `ConversationProvider` holds:
- `List<Message> _messages`
- `bool isLoading`
- `String? lastModelId`
- Methods: `sendMessage`, `handleAction`, `newConversation`

The chat screen becomes a thin Consumer with widget composition.

## 9. Component Rendering with Null/Error Safety

Each component builder follows this contract:
1. If required `data` fields missing → render error fallback (sized box with debug label)
2. If children list is null/empty → render without children
3. If action dispatch is null on interactive component → render in disabled state
4. Wrap in `Builder` for `BuildContext` access

Component builders never throw. Errors are caught at the `WidgetRegistry.build()` level and rendered as an error placeholder.

---

## 10. Performance Considerations

1. **Component recycling**: ContentBlocks have `id` fields for key-based recycling
2. **ListView cache**: ConversationStream uses `cacheExtent: 500` (same as current)
3. **Image caching**: `flutter_cache_manager` already in use for model metadata; extend to component images
4. **Chart caching**: `fl_chart` doesn't redraw on parent rebuild (uses RepaintBoundary)
5. **Lazy component registration**: WidgetRegistry only builds registered types; unregistered types show fallback
6. **Stream throttling**: Keep existing 100ms throttle for text events; ui_blocks events are discrete (no throttling needed)

## 13. Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| LLM-generated UI blocks could be malformed | WidgetRegistry uses try-catch; fallback to error placeholder |
| MCP servers may not adopt new content types | Component system degrades gracefully — unknown types render as text |
| Performance regression with complex component trees | ConversationStream uses recycling; heavy components (charts) use RepaintBoundary |
| Interactive actions could be abused (rapid clicking) | ActionHandler debounces per-component by ID; server-side rate limiting |
| Grocery mode integration loses features | Keep inline_search.dart + cart_product_card.dart; render in component context |
| Large image blocks from MCP | Image component has max dimension constraints + progressive loading |
